# 发压容量标定：harness vs wrk（闭环）

> 结果文件：`crossval-closed-20261019-115826.json` · 判定：**PASS**

**问题**：同一个 HTTP 目标、闭环同一并发，harness 与 wrk 各自能压到多少、瓶颈在哪一侧——发压容量标定

**结论**：harness 闭环发压上限约 124,000 req/s（本机、1024 字节、64 连接）；wrk 测得的服务端上限约 215,000 req/s。

## 设置

| 项 | 值 |
|---|---|
| 目标 | `http://127.0.0.1:19180/echo`，POST 1024 字节，原样回显 |
| 负载 | 闭环 64 并发，harness 连接 64 条 |
| harness | 口径卡 `crossval-http-closed-capacity-v1`，结果 `crossval-http-closed-capacity-v1-20261019-115423.json`，正式轮第 3 轮，统计窗口 [20s, 60s]；全部轮次有效 true，client_bound true |
| wrk | `taskset -c 5-9 wrk -t 4 -c 64 --latency -s bench/bin/post-1k.lua -d 40s http://127.0.0.1:19180/echo`（wrk 4.2.0-dirty [epoll] Copyright (C) 2012 Will Glozer） |
| CPU 亲和 | 服务端 0-4 · 压测端（harness 与 wrk）5-9 · 可用 / 主机核数 5 / 10 |
| 机器 | localhost，AMD Ryzen 5 4600H with Radeon Graphics，git 77d04f2 |

## 说明

- 闭环吞吐对比不是测量校验而是容量标定：闭环下吞吐 = 并发 / 往返时延，JVM 同步调用的 harness 每次调用要在发压虚拟线程与 Netty IO 线程之间交接两次（写出、唤醒），这份固有开销决定了它的闭环上限；wrk 在单个 epoll 线程里收发，常常先压满服务端。延迟各列只作信息项（wrk 闭环不做 CO 修正）。
- CPU：harness 一侧取正式轮统计窗口内的 /proc/stat 采样（rounds[].cpu）；wrk 一侧取测量运行中段的采样。
- 请求体：harness 发 1024 字节固定种子随机内容，wrk 发 1024 字节固定内容（bench/bin/post-1k.lua）；回显开销与内容无关。
- 数字来自固定的一台本机，只用于校验 harness 与第三方工具，不代表 RPC 框架的性能。
