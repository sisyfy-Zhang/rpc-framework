## 可能原因

- 测量起点之后的客户端开销：harness 的服务时间从发压虚拟线程开始执行算起，含虚拟线程调度、（连接都忙时的）排队、写出与唤醒两次跨线程交接；wrk2 的未修正延迟在单个 epoll 线程里从写出算起。

## 说明

- 相对偏差 = |harness − wrk2| / wrk2（以第三方工具为参照）。harness 取正式轮（开环：窗口 p99 的中位数那一轮），统计窗口 [20s, 60s]；wrk2 先预热跑一次丢弃，再带 -U 测一次（同一次运行同时给出修正后与未修正分布），测量时长与 harness 的窗口长度相同。
- wrk2 的发送节拍是毫秒粒度：giltene/wrk2@44a94c1 的 src/wrk.c 第 604 行 `int msec_to_wait = round((time_usec_to_wait / 1000.0L) + 0.5);` 把距下次计划发送的等待向上取整到整毫秒，第 608–609 行 `aeCreateTimeEvent(thread->loop, msec_to_wait, delay_request, c, NULL)` 用 ae 定时器推迟发送，而 ae 的定时器本身按毫秒计时（src/ae.c 第 150–170 行 aeGetTime / aeAddMillisecondsToNow）。每个请求都比计划时刻晚发零点几到一毫秒多，这段滞后按修正口径计入 wrk2 的“修正后”延迟，所以它不能做亚毫秒级开环延迟的参照；“未修正”延迟从实际发出计时，不含这段滞后。
- harness 的修正后延迟（从计划时刻）= 服务时间 + 发出滞后；发出滞后由判定项 c 独立约束，所以服务时间与 wrk2 未修正延迟一致、发出滞后受控，就说明 harness 的开环延迟可信。修正后延迟两列只作信息项并排，不判定。
- p99.9 与 max 不参与判定。
- 请求体：harness 发 1024 字节固定种子随机内容，wrk2 发 1024 字节固定内容（bench/bin/post-1k.lua）；回显开销与内容无关。
- 数字来自固定的一台本机，只用于校验 harness 与第三方工具，不代表 RPC 框架的性能。
