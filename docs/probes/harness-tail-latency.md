# harness 开环尾延迟对照实验（任务 10，阶段 2 准备项 1）

找出 harness 开环发压路径上自身的尾延迟来源并消除，使交叉验证开环卡（`crossval-http-open-v1`，HTTP 5000 req/s、64 连接、1KB）
在**不放宽阈值**的前提下稳定通过。数据来自 `bench/bin/crossval.sh --mode open`（harness 跑卡 → wrk2 `-U` 打同一 URL → `crossval` 判定），
每组的原始 JSON / Markdown 在 WSL 的 `~/t10/<实验名>/`（不入库）；本文的表格由那些 JSON 机械整理（`table.py`），数字未改动。

## 目的

d5d620c 的三次正式归档里，开环交叉验证都 FAIL 在 b 项 p99：harness 服务时间 p99 0.52~0.57ms，wrk2 `-U` 未修正 p99 0.37ms
（差 150~200µs，判据是相对偏差 ≤ 15% **或**绝对差 ≤ 100µs）。两端 GC 已排除（停顿 ≤ 窗口 0.05%）。要回答：

1. 多出来的尾巴是 harness 哪一段造成的：发压线程模型（每请求新虚拟线程）、客户端 IO 线程数、调度线程与其它线程抢核、冷 JVM 的第一段？
2. 环境本身（WSL2）的 p99 漂移有多大——用来解释，不用来放宽阈值。

## 方法

先把每个变量做成 `run` 的命令行选项（缺省 = 当时的行为），经 `BENCH_HARNESS_OPTS` 传给 `crossval.sh`，不改代码就能复现每一组：

| 变量 | 选项 | 取值 |
|---|---|---|
| E1 发压线程模型 | `--open-workers` | `per-request`（每请求一个新虚拟线程，基线）/ `pool`（N = 连接数个虚拟线程工作者，有界 FIFO 队列）/ `pool-platform`（工作者为平台线程，追加） |
| E2 客户端 IO 线程 | `--io-threads` | 5（基线 = 可用核数）/ 2 / 1；追加 `--io-busy-poll on`（事件循环忙轮询，不阻塞、不需要被唤醒） |
| E3 调度线程独占一核 | `--pin-dispatcher 5` | 调度线程（`bench-dispatch`）钉到 cpu5，进程里其余线程钉到 6-9；每轮读回各线程 `Cpus_allowed_list` 核实 |
| E4 正式轮前预热段 | `--pre-warmup` | 0（基线）/ 卡片 warmup（短卡 10s、正式卡 20s） |
| E6 HTTP 客户端（追加） | `--http-client` | `netty`（事件循环，基线）/ `blocking`（每连接一个阻塞 Socket，调用方线程自己收发） |
| E5 噪声地板 | — | wrk2 同一时段连跑 2 次；harness 基线连跑 2 次；`Hiccup`（钉核忙等读 `nanoTime`，记录线程没跑上的空洞） |

- **短卡**（迭代用）：`crossval-http-open-short`（不入库），每轮 30s、预热 10s、窗口 [10s, 30s]、3 轮；wrk2 预热 10s + 测 20s。
- **正式卡**：仓库的 `crossval-http-open-v1`（每轮 60s、预热 20s、窗口 [20s, 60s]、3 轮；wrk2 预热 20s + 测 40s），用来确认结论。
- 每组记录正式轮（3 轮 p99 中位那一轮）的服务时间 p50 / p99 / p99.9 / max、发出滞后 p99、最大在途、backlog、两组核的 CPU、
  客户端 GC 停顿，另列 3 轮各自的服务时间 p99（看可重复性）。"p99 差" = harness 服务时间 p99 − wrk2 未修正 p99，判据要求 ≤ 100µs
  （或相对 ≤ 15%，这里 wrk2 约 0.35ms，两条里绝对差更宽）。

## 结论

逐个变量（数字见上表；"有效 / 无效"按对 b 项 p99 差与轮间稳定性的贡献判断）：

- **E1 发压线程模型：pool 有效**。p99 差 283 → 171µs，p99.9 6.4 → 2.6ms；与绑核组合时 pool（C2、C1）也都好于 per-request（C3）。
  每请求新虚拟线程意味着每个请求都有一次虚拟线程创建 + 首次调度，突发（调度线程被推迟后补发一串）时这批新线程同时抢载体；
  固定工作者只是被唤醒去取下一个计划时刻。平台线程工作者（C5、C7）没有更好，p50 反而高约 30µs，保留为选项、不做缺省。
- **E2 IO 线程数：单独改无明显作用**。5 → 2 时 p99 差 124µs，5 → 1 时 218µs，在轮间起伏之内（E2 io=1 的三轮 0.51~0.86ms）。
  真正起作用的是**忙轮询**：IO 线程不再阻塞在 `epoll_wait` 里，调用方提交写出时不用唤醒它，服务时间 p50 从约 0.22ms 降到 0.147ms，
  与 wrk2 未修正 p50 重合——此前所谓"两次线程交接约 75µs 的固定开销"，大部分就是这一次唤醒。忙轮询只配 1 个 IO 线程（占 1 个核）。
- **E3 调度线程独占一核：有效**。发出滞后 p99 0.18 → 0.04ms，服务时间 p99.9 / max 6.4 / 26ms → 0.66 / 3.2ms，p99 差 283 → 105µs。
  调度线程是忙等的，不钉时 Linux 会把被唤醒的 IO 线程 / 载体线程放到它所在的核上，被唤醒方要等忙等线程让出时间片；钉开之后，
  它被推迟只表现为发出滞后，不再拖累别人。
- **E4 预热段：HTTP 卡上作用小于环境噪声，RPC 卡上作用决定性**。HTTP 卡的预热段 p99 常在 1~14ms、最大在途 30~150，第 1 轮仍可能撞上
  环境停顿；RPC 卡（第 7 节）的冷启动突发是半秒级、几千个在途，挪进预热段之后第 1 轮 p99 从 52.6ms 降到 3.5ms、最大在途从 4220 降到 387。保留为缺省。
- **E6 阻塞客户端（追加）：最稳**。没有 IO 线程交接、没有忙等的 IO 线程，正式轮服务时间与 wrk2 未修正值的差在 ±30µs 以内，各轮起伏也最小；
  必须配平台线程工作者。
- **E5 噪声地板**：wrk2 的 p99 在 2 小时里只漂 0.05ms，harness 同一配置的单轮 p99 却在 0.40~0.75ms 之间跳（偶发 1~3ms）。
  差别来自忙等：harness 有两个一直在跑的线程（调度线程、忙轮询的 IO 线程），它们所在的 vCPU 被宿主抢走的那几毫秒里，
  在途请求全部挂起；wrk2 的线程大部分时间在睡，被唤醒时调度器给它一个空闲的 vCPU，很少撞上空洞。
  这既是 harness 的 p99.9 / max 比 wrk2 大一个数量级的原因，也决定了"各轮 p99 落在 0.40~0.48ms"这一残余起伏。

最终缺省（见下节）：rpc 卡 `pool`（虚拟线程工作者）；http 开环卡阻塞客户端 + `pool-platform`；Linux 绑调度线程；预热段 = 卡片 warmup。
harness 自身在正式卡上的 b 项偏差已降到 ±30µs，剩下决定判定的是那一次运行（两边任一边）撞上多少宿主停顿：5 次正式运行 2 次 PASS，
没有达到"连续 3 次"。阈值没有放宽。

## 对设计的影响

- **缺省值改为实证有效的组合**：rpc 卡 `--open-workers pool`；http 开环卡 `--http-client blocking` + `pool-platform`（http 闭环卡保持
  netty 客户端、IO 线程 = 可用核数、不忙轮询：闭环卡标定的是 harness 的发压容量）；`bench-run.sh` 在 Linux 绑核启动时缺省
  `--pin-dispatcher <压测端第一个核>`；预热段缺省 = 卡片 warmup。保留为选项：`per-request`、netty 客户端的 `--io-threads` / `--io-busy-poll`、
  虚拟线程工作者配阻塞客户端。
- **交叉验证前提改为"有效轮 ≥ 2"**（裁定）：被 `dispatcher_delayed` 判无效的轮本来就是为排除环境停顿设的，正式轮只在有效轮里选；
  有效轮 < 2 时证据不足判 FAIL。b 项 15% / 100µs 不变。
- **新规则 `dispatcher_delayed`**：开环轮内发出滞后 p99 > 1ms 的轮判无效、不参与正式轮选取（E4 第 3 轮就是这样的一轮）。
- **HTTP 对照端只验证 harness 的计时 / 调度 / 直方图**。阻塞客户端（以及 netty 忙轮询）都是 HTTP 适配器——harness 自己的代码——上的改动，
  去掉适配器的线程交接，是让交叉验证比较"驱动与计时"本身；RPC 卡的路径仍是 `RpcClient`（Netty NIO，`NioEventLoopGroup(0)` = 2 × 核数，
  没有可配项）+ 虚拟线程工作者池，客户端里的线程交接是被测框架的一部分，照常计入——这正是 RPC 卡要测的东西。
- **harness 的 CPU 占用**：开环调度线程占满一个核；http 阻塞客户端时压测端 5 核平均忙 25~39%（netty 忙轮询时 44%）。
  `client_bound` 判定（> 90%）不受影响；绑核划分仍是服务端 0-4、压测端 5-9。
- **参照端对称口径（已裁定采纳）**：#4 说明参照端同样受环境停顿影响。crossval 改为 wrk2 测 3 次（各 20s 预热 + 40s）、取未修正 p99 的中位
  作对照值，三次都写进结果（`crossval/3`），前提要求三次都无 socket 错误。本节的正式结果是改口径之前跑的，按单次 wrk2 判定；
  "连续 3 次 PASS"按新口径在任务 13 正式归档时检验。
- **建议（待裁定）**：若希望 RPC 卡也能做 IO 线程数的对照，`RpcClientConfig` 需要一个事件循环线程数的配置项（现在只能靠全局的
  `-Dio.netty.eventLoopThreads`，会同时影响进程里所有缺省大小的 Netty 线程组）。
  （任务 11 已落实：`RpcClientConfig.ioThreads` / `RpcServerConfig.ioThreads`，starter 属性 `rpc.client.io-threads` / `rpc.server.io-threads`，
  harness 的 `--io-threads` 对 rpc 卡生效；见 docs/benchmarking.md 的 harness 实现选项。）

## 重跑

```bash
# 正式卡，缺省选项（即最终缺省）
bash bench/bin/crossval.sh --mode open
# 任一单变量组：用 BENCH_HARNESS_OPTS 覆盖，例如 E0 基线
BENCH_HARNESS_OPTS="--http-client netty --open-workers per-request --io-threads 5 --io-busy-poll off --pin-dispatcher off --pre-warmup 0" \
  bash bench/bin/crossval.sh --mode open
# 短卡：把 crossval-http-open-v1.yaml 复制成 crossval-http-open-short.yaml，改 profile id、duration 30s、warmup 10s、
# steady_window [10s, 30s]，并设 CROSSVAL_TOOL_WARMUP=10 CROSSVAL_TOOL_DURATION=20
bash bench/bin/crossval.sh --mode open --profile <短卡路径>
```
