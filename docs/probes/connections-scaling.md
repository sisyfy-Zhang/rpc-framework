# 连接数递减探针（任务 21）

问题：闭环 128 并发、每节点 2 → 4 → 8 条连接时，吞吐为什么是 141k → 139k → 126k（[bench/reports/20261022-d23e39d/NOTES.md](../../bench/reports/20261022-d23e39d/NOTES.md)「观察：连接数扫描」）。
预登记假设 H1 ~ H4（D-051），数据裁决；归因到 1 ~ 2 项即算成功，归不出就写"未定论"。

**结论**：本次能归因。两端每次 IO 事件循环唤醒能处理的请求数随连接数增加而变少：连接数 ×4 时，每请求的读写系统调用、IO 线程自愿切换与 IO 线程 CPU
在两端都成倍上升。压测端与服务端的其它线程组每请求 CPU 基本不变。增加的开销全部落在 `netty_io` 上：压测端 +12.0 µs/请求，服务端 +10.2 µs/请求。
抢核（非自愿切换）随之上升，但只是次要项。H1、H3 支持；H2 部分支持（份额变化成立，但被拖慢的不是载体线程）；H4 间接支持。
缺省 `connectionsPerNode = 2` 不改：在本负载下它吞吐最高、两端每请求 CPU 最低、p99 最低。

- 两端 IO 线程数都取 Netty 缺省（2 × 5 = 10），只有 io2 变体例外。事件循环线程懒启动，所以实际在干活的只有"连接数"个。

## 口径说明

- **服务端统计经 HTTP 控制端点取**：`sweep.sh` 给服务端另开 `--http-port`（19400），窗口起止的服务端统计经 `GET /stats` 取（在 IO 线程上回答、不经业务执行器），
  见 [benchmarking.md「并发扫描与连接数扫描」](../benchmarking.md#并发扫描与连接数扫描)。
- **`netty_io` 线程数口径变了**：控制端点让服务端 `netty_io` 组多出几乎空闲的 `bench-http-boss` 与 `bench-http-worker` 线程，CPU 可以忽略
  （冒烟：c2 服务端 `netty_io` 9.36 µs/请求，经 RPC 取统计时 9.47）。
  另外窗口内会再 **+1**（例如 c2 是 7 -> 8）。推测原因：JDK HttpClient 的 HTTP/1.1 空闲连接保活时长短于 35s 的窗口，窗口结束时那次 `GET /stats` 新建了连接，
  落到下一个 `bench-http-worker` 上（最多 10 个），所以窗口起点的线程数也随轮次累积（5 ~ 13）。
  因此本文的 `netty_io` 线程数只作参考，不能与任务 20 及更早的结果直接比；本文的论证只用每请求的 CPU 与切换。
- **压测端 `other` 组**：多了 JDK HttpClient 的 3 ~ 4 个线程（取统计用），约 0.05 µs/请求。
- **各组 CPU 之和低于核忙碌率折算值**：`by_group.<组>.cpu_ms` 是存活线程的 `utime + stime`，而 `rounds[].cpu` 的忙碌率按核计，还包含没有记到任何线程头上的时间
  （推测主要是 loopback 收包的 softirq）和同组核上的其它进程。冒烟里 c8 压测端按线程求和 37.9 µs/请求，按核忙碌率折算约 50.8 µs/请求。
  所以 H2 / H3 用**组间份额随连接数的变化**来论证，不拿两种量法直接相减。
- **`jvm` 组可能出现负值**：JIT 的动态编译线程在窗口内退出、又新建同名线程时，退出线程累计的 CPU 会从结束快照里消失（冒烟里 c8 压测端 `jvm` 组 −3.29 µs/请求）。
  这与切换计数同一口径，该端的 `cpu_ms` 也随之略偏低。正式轮里没有出现。
- `syscw` 包含 eventfd 唤醒（Netty 的 `selector.wakeup()`），不等于套接字写次数。

## 假设逐条

### H1 flush 合并效率随连接数下降 —— 支持（而且不只是写，读与唤醒同样变多）

- `syscw/请求`：压测端 0.16 → 0.44 → 0.62（×3.9），服务端 0.11 → 0.25 → 0.40（×3.6）。
- 读侧增长得更多：`syscr/请求` 压测端 0.057 → 0.228 → 0.410（×7.2），服务端 0.097 → 0.268 → 0.425（×4.4）。
- IO 线程的自愿切换也一样：压测端 `netty_io` 0.023 → 0.115 → 0.250 次/请求，服务端 0.044 → 0.128 → 0.257 次/请求。
  每次自愿切换大致对应事件循环在 `epoll_wait` 里睡一次。按倒数算，每次唤醒平均处理的请求数：压测端从约 43 个降到约 4 个，服务端从约 23 个降到约 4 个。
- 128 个在途请求分到 8 条连接、8 个事件循环上，每个循环每次醒来只拿到很少的帧。所以每请求的读、写（含 flush 合并后剩下的写）和唤醒都成倍增加，
  flush 合并能合并的东西也随之变少。
- 口径：`syscw` 含 eventfd 唤醒；自愿切换只是"唤醒次数"的近似。

### H2 压测端 IO 线程与载体线程争核 —— 部分支持

- **份额变化成立**。压测端各组 CPU 之和里，`netty_io` 的占比 53% → 64% → 69%，`fjp` 47% → 36% → 31%。压测端核忙碌率 64% → 76% → 86%。
- **但被拖慢的不是载体线程**：
  - `fjp` 每请求 CPU 几乎不变（10.3 → 10.9 → 10.7 µs），自愿切换反而略降（0.152 → 0.107）。
  - 压测端每请求多出来的 12.5 µs 里，12.0 µs 在 `netty_io`。
- **抢核存在，但是次要项**：非自愿切换（被抢占）`netty_io` 0.002 → 0.057、`fjp` 0.011 → 0.025 次/请求，量级远小于自愿切换的增量。
- **io2 变体（8 条连接落在压测端 2 个事件循环上）**：
  - 压测端 `netty_io` 每请求 CPU 从 23.6 降到 16.0 µs，自愿切换从 0.250 降到 0.008（每次唤醒处理约百个响应）。压测端 syscw 0.62 → 0.28，核忙碌率 86% → 66%。
  - 但吞吐没有回升：119.1k 对 122.9k，单次运行，−3%，在 c4 / c8-direct 的波动幅度之内，不能当作有差别。
  - p50 从 0.83 升到 1.00 ms：2 个循环串行处理 4 条连接，单请求排队变长。p99 反而降到 2.62 ms（单次运行）。
  - 服务端一侧与 c8 相同：`netty_io` 16.6 µs，自愿切换 0.280，syscw 0.41。
- **结论**：压测端 IO 线程的 CPU 是**放大项**——它把压测端的核占用从 66% 推到 86%，但不是唯一瓶颈。把它压回去之后，吞吐仍停在 c8 的水平，
  剩下的是服务端同样的单次唤醒处理量下降（H3），以及 2 个循环的串行排队。本实验无法再把这两者分开。

### H3 服务端 `netty_io` 同理 —— 支持

- 服务端 `netty_io` 7.44 → 13.33 → 17.61 µs/请求（×2.4，+10.2 µs）；`biz_pool` 9.33 → 10.81 → 9.72，基本不变。
- 服务端每请求 CPU 之和 16.91 → 24.31 → 27.43 µs，增量几乎都在 `netty_io`。服务端核忙碌率 52% → 62% → 69%，没有饱和。
- `netty_io` 在服务端各组 CPU 之和中的占比：44% → 55% → 64%。
- **direct 变体排除了业务池**：
  - 没有业务池时，服务端 `netty_io`（此时含业务方法）从 c2 的 6.53 µs 涨到 c8 的 17.04 µs，自愿切换 0.021 → 0.138。增量（+10.5 µs）与 fixed 时相同。
  - 所以服务端的增量在 IO 循环本身，与执行器交接无关。
  - c8-direct 被判为 `client_bound`，它的吞吐（144.7k，两次差 6.4%）不用于比较。

### H4 任务 11 的"随连接增长"是 flush 合并之前的现象 —— 支持（间接证据，没有重跑旧版本）

- 任务 11（flush 合并之前，20s 卡，不作数）：每节点 2 / 4 / 8 条连接 = 103.1k / 109.5k / 119.6k，c8 为 `client_bound`（压测端核 92%）。
- [flush 合并探针](flush-and-executor.md)（closed64）：合并关闭时两端每请求 `write` 都约 1.0，与连接数无关；合并打开后降到 0.09 ~ 0.19。
  单连接从 68.6k 升到 98.5k，2 连接从 89.4k 升到 107.2k。
- 推论：
  - 合并之前，每请求的写次数固定在约 1 次，加连接不增加每请求开销，只增加并行的事件循环，所以吞吐随连接增长。
  - 合并之后，每请求的读写与唤醒次数取决于每条连接的批量（H1），加连接会稀释批量，每请求开销上升，于是吞吐下降。
  - 合并后 2 条连接的 143.0k 已超过合并前 8 条连接的 119.6k。
  - 同一构建里并发 128 → 256（2 条连接）吞吐 141k → 162k（d23e39d），也符合"每条连接的批量越大越省"。
- 局限：没有用旧版本重跑，任务 11 的数字是 20s 卡且不作数，所以只能算"与数据一致"的间接支持。

## 结论与建议

1. **归因（两项）**：
   - ① 连接数增加稀释了两端每个事件循环每次唤醒的批量：每请求的读写系统调用与唤醒次数成倍增加（H1）。
   - ② 这些开销全部表现为两端 `netty_io` 每请求 CPU 上升（客 +12.0 µs，服 +10.2 µs），其它线程组基本不变（H2 份额 / H3）。
   - 两端核都没饱和（86% / 69%）；闭环下每请求开销与排队变长直接换算成更低的吞吐和更高的 p99（2.17 → 4.54 ms）。
2. **缺省 `connectionsPerNode = 2` 不改**。依据：本负载（闭环 128、1KB、单提供者、同机）下 c2 的吞吐最高（143.0k，比 c8 高 16%），
   两端每请求 CPU 最低（22.0 / 16.9 µs，c8 是 34.4 / 27.4 µs），p99 最低。
   调研候选 #8（缺省 2 → 4）的前提——"按任务 11 扫描，吞吐随连接数提升"——在 flush 合并之后不再成立。
3. **建议修改 [benchmarking.md](../benchmarking.md#并发扫描与连接数扫描) 里关于连接数的说法**（由 Fable 裁定）。
   那段描述的是任务 11 冒烟的观察："限制吞吐的是连接数……把每节点连接数加到 8 之后……瓶颈转到压测端"。flush 合并之后，在闭环 128 下这个结论不再成立。
4. **适用范围**：本结论只覆盖同机 loopback、单提供者、1KB、闭环 128 并发。
   多个客户端进程分摊、跨机（真实网卡延迟让每次唤醒积累更多帧）、或者业务方法耗时远大于 IO 开销时，连接数的取舍可能不同，本次没有测。

## 局限

- c4（4 次）与 c8-direct（2 次）的吞吐不满足 5% 的稳定口径（见"重复性"），只用作中间点与服务端分组参考。
- 变体 c8-io2 与 c2-direct 只跑了 1 次。
- 宿主状态不受控（WSL2 + 桌面 Windows），c4 第 2 次的两端每请求 CPU 整体抬高、原因不明，这类波动会影响 ±10% 量级的吞吐比较。
- 各组 CPU 只统计存活线程的 `utime + stime`，不含 softirq（见"口径说明"），所以分组之和不等于核忙碌率。
- "每次唤醒处理的请求数"是用自愿切换倒推的近似值，没有直接统计 `epoll_wait` 的返回次数。
- H4 没有重跑 flush 合并之前的版本。
