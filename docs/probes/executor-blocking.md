# 虚拟线程 vs 固定池：阻塞型业务负载下该选哪个（任务 20，阶段 4a）

回答阶段 4a 第二项："什么负载下该把服务端执行器从缺省固定池换成 virtual、代价是什么"，并量出 JDK 21 虚拟线程在 `synchronized` 内阻塞时的钉住退化
（JEP 491 在 JDK 24 才修）。业务方法用 `server --work` 模拟 IO 等待（占着执行业务方法的线程、不占 CPU），等待方式由 `--work-mode` 选
（`park` / `monitor` / `sync-park`，卡片字段 `target.server_work_mode`，见 [benchmarking.md](../benchmarking.md#字段说明)）。
每对卡只差一处，判定在跑之前登记（个别条目在看到机制后、跑之前改述，见第 7 节），跑完逐条对照。**数字是探针口径**（工作区有未提交改动，`git_dirty = true`），只给机制、数据与结论。

**结论**：

- **阻塞时间 × QPS 超过固定池线程数时，virtual 吞吐按并发线性增长，固定池卡在"线程数 / 阻塞时间"**：业务等 2ms、闭环 64 并发，fixed 4.6k req/s、
  virtual 23.9k（**5.1×**），p99 15.3 → 3.3ms；等 10ms、闭环 256，fixed 973 req/s（= 10 线程 / 10ms 的容量）、成功请求 p50 266ms 几乎全是排队（排队等待 p50 256ms），
  virtual 22.4k（**23×**），p99 268.7 → 12.7ms。两组 virtual 的每请求服务端 CPU 都**更低**（55 vs 150 µs、33 vs 220~257 µs），上下文切换 / 请求也更少。
- **没超过时 virtual 没有优势**：开环 3000 req/s、业务 2ms（固定池约 62% 利用率），固定池排队等待 p99 只有 0.1 ~ 0.4ms，两边 p99（2.7 ~ 5.5ms）与 p99.9 在同一噪声带里，
  每请求 CPU 相当（1.08×）。
- **固定池过载时会"拥塞崩溃"，virtual 不会**：闭环 1500 并发、业务 10ms（在途 1500 > 10 线程 + 队列 1000），fixed 每秒约 **8.4 万次 SERVER_OVERLOADED 拒绝**，
  排队到执行的请求要等约 1s、正好超过调用方 1s 超时——服务端仍以满容量（约 1k/s）在干活，但**成功只有每轮 2 ~ 17 个**（吞吐 ≈ 0）；virtual 同负载 93.6k req/s、0 错误。
  条件式：**排队上限 × 业务时长 / 线程数 ≥ 调用超时 → 过载时 goodput 归零**（缺省队列 1000 不改；按"排队等待远小于超时"配线程与队列）。
  根治要靠"感知排队等待的准入 / 自适应并发限制"（排队等待接近剩余 deadline 时直接拒绝，而不是只看队列长度），列为阶段 4b 候选。
- **JDK 21 钉住**：`synchronized` 内 `Object.wait` → 调度器**补偿**，载体线程从 5 扩到 **256**（服务端线程 31 → 281），吞吐 23.0k 与 park 持平，代价是每请求 CPU
  4.4×（146 vs 33 µs）、业务线程组上下文切换 8.7×；`synchronized` 内 park → **钉住且不补偿**，载体保持 5 个，吞吐 **464 ~ 480 req/s**（= 5 / 10.4ms），
  排队等待 p50 约 0.5s、每轮 275 ~ 999 个超时。
- **测量陷阱**：锁对象若是方法内 new、从不外泄，C2 会把 synchronized 整个消除（lock elision），JIT 之后钉住凭空消失（第 6 节，[pitfalls 38](../pitfalls.md)）。

说明服务端还有余量。**这组 virtual 的数字是"受压测端并发限制"的下界**，不是服务端上限。

| park（B 组） | virtual-1 / -2 | 22 444.5 / 22 428.8 | 11.36 / 12.67 · 11.37 / 12.73 | 0 | 14.9% | 33.1 | 0.22 | **5**（31） | 19 | 0.05 / 0.19 |
| monitor | monitor-1 | 23 009.3 | 10.838 / 14.066 / 53.510 | 0 | 67.1% | 145.8 | 1.88 | **256**（281） | 28 | 0.076 / 0.872 |
| monitor | monitor-2 | 22 769.2 | 10.936 / 15.417 / 21.676 | 0 | 67.2% | 147.6 | 1.88 | **256**（281） | 38 | 0.087 / 1.229 |
| sync-park | syncpark-1 | **469.0** | 482.869 / 990.904 / 1000.342 | 726 timeout | 4.6% | — | 1.09 | **5**（31） | 3 | 503.3 / 1002.4 |
| sync-park | syncpark-2 | **472.0** | 462.160 / 994.574 / 998.244 | 629 timeout | 4.3% | — | 1.11 | **5**（31） | 2 | 522.2 / 998.2 |

- **`synchronized` 内 `Object.wait`（monitor）**：虚拟线程不能在持有监视器时卸载，但 JDK 21 把 `Object.wait` 当作"会占住 OS 线程的阻塞操作"做了**补偿**：
  调度器临时加载体线程（上限 `jdk.virtualThreadScheduler.maxPoolSize`，缺省 256）。256 个并发全部在等，载体就扩到 256 个——吞吐与 park 持平（23.0k / 22.8k vs 22.4k），代价是**线程数**（服务端 31 → 281）、**每请求 CPU 4.4×**（146 vs 33 µs，服务端核 67%）、业务组切换 8.7×（每次等待都是一次真正的
  平台线程阻塞 / 唤醒）、GC 停顿 1.5 ~ 2×。并发再往上，超过 256 的部分就会像 sync-park 一样排队。
- **`synchronized` 内 parkNanos（sync-park）**：钉住且**不补偿**——载体保持 5 个，同一时刻最多 5 个请求在"等"，吞吐 = 5 / 10.4ms ≈ 480（实测 464 ~ 480，全部 6 轮），
  其余 251 个虚拟线程排在调度队列里（排队等待 p50 约 0.5s、p99 到 1s），每轮 275 ~ 999 个请求排过了 1s 超时。这就是 JEP 491 修掉的退化；JDK 21 上
  synchronized 内的 `Thread.sleep`、`LockSupport.park`（JUC 锁、队列、future 的等待都落到它）都属于这一类（Windows 小探针：sync-park 与 sync-sleep 都是 313 ops/s，
  `Object.wait` 是 16.0k、载体 256）。
- 两种方式都没有一次执行器拒绝：虚拟线程模式的许可（10000）在派发时取得，钉住发生在许可之后，拒绝语义看不到它。

| 运行 | 吞吐 (req/s) | 窗口成功（三轮） | 窗口错误（正式轮） | p50 / p99 (ms) | CPU 压测端 / 服务端 | 备注 |
|---|---|---|---|---|---|---|
| fixed-1 | **0.3**（三轮 0.1 / 0.5 / 0.3） | 2 / 17 / 9 | 2 895 617 SERVER_OVERLOADED + 35 093 timeout | 1008.206 / 1013.449 | 68.3% / 31.2% | 服务端统计 unknown（见下） |
| virtual-1 | **93 560.9**（三轮 95.2k / 93.6k / 92.8k） | — | 0 | 15.262 / 28.230 | 49.1% / 47.0% | 不是 client_bound；CPU µs/请求 25.1，服务端 GC 148ms / 35s |

1500 个在途 > 10 线程 + 1000 队列：超出的约 490 个**立即**被拒（SERVER_OVERLOADED，业务未执行），闭环虚拟用户收到拒绝马上重发，于是每秒约 8.4 万次拒绝；
挤进队列的请求要等 1000 × 10ms / 10 = **1.0s** 才开始执行，执行完时调用方的 1s 超时已经到了——服务端每秒仍完成约 1 000 个业务调用（timeout 计数 ≈ 1003/s），
但几乎全部作废，**成功每轮只有 2 ~ 17 个**。这是有界队列 + 超时的拥塞崩溃：**排队上限 × 业务时长 / 线程数 ≥ 调用超时时，队列里的请求必然白做**。
有界队列的价值（[fault-injection.md 突增一节](fault-injection.md#3-突增fault-burst3x-bounded-v1--fault-burst3x-unbounded-v1)）建立在"排队上限 × 服务时间 / 线程数远小于超时"上：
那里业务 1ms、排队上限的等待约 0.1s。缺省 1000 的队列配 10ms 的业务、1s 的超时就踩在边界上。
virtual 同负载 93.6k req/s、0 错误（1500 / 15.3ms ≈ 98k，接近压测端并发上限；两侧核都在 50% 以下）。

**测量局限**：fixed 这一行的服务端统计（执行器拒绝、排队等待、上下文切换、GC）是 unknown——harness 经 `BenchService.stats()` 这个 RPC 取服务端统计，
它与业务请求走同一个已经饱和的执行器，同样被拒。拒绝数取自压测端的错误分类（`status:SERVER_OVERLOADED`）。故障卡用的 HTTP 控制端点（`--http-port`，IO 线程回答）
能绕开这一点，sweep.sh 没有接它。

## 6. 测量陷阱：锁对象必须逃逸（lock elision）

第一版 sync-park 写成 `Object lock = new Object(); synchronized (lock) { parkNanos(...); }`。12s 冒烟的每秒成功数：474、481、480、477、481、480、482、451、441、
692、1621、**22 046**——前 9 秒是钉住的约 480，C2 编译 `work()` 之后跳到 22k。逃逸分析认定局部 new、从不外泄的锁对象不可能被别的线程同步，把
`monitorenter / monitorexit` 整个消除（`-XX:+EliminateLocks` 缺省开），JIT 之后测的是"没有 synchronized"。Windows 上 3 秒的小探针来不及触发 C2，所以没暴露。
修法：每次新建的锁对象写进一个 volatile 静态字段（全局逃逸），仍是每请求一把锁、不引入锁竞争（`BenchServiceImpl.escapedLock`）；修复后全程稳定在 470 左右。
`monitor` 不受影响（对象作为接收者传进 native 的 `wait`，已经逃逸）。教训见 [pitfalls 38](../pitfalls.md)。

## 8. 何时选 virtual，代价是什么

**选 virtual**：业务方法以阻塞等待为主（同步调下游 RPC / HTTP / JDBC），且**阻塞时长 × QPS > 固定池线程数**（缺省 2 × 核数）——此时固定池吞吐被
"线程数 / 阻塞时长"封顶、延迟变成排队时间，virtual 吞吐随并发线性增长、每请求 CPU 还更低。
没超过（固定池利用率中等以下）时两者没有可分辨的差别，保持缺省即可；纯 CPU、微秒级的方法也不需要它。

**代价**：

- **JDK 21 的 synchronized**：业务代码（含依赖库）在 `synchronized` 内阻塞会钉住载体。`Object.wait` 有补偿——载体扩到最多 256 个平台线程，吞吐暂时不掉，
  但线程数与每请求 CPU 回到"平台线程每请求一个"的水平（本实验 4.4×）；park / sleep 没有补偿——同时阻塞的请求数被核数封顶（本实验 480 req/s，
  比固定池的 973 还低一半）。JDK 24（JEP 491）之前，换 virtual 之前要先查 synchronized 内的阻塞调用（`-Djdk.tracePinnedThreads=full`），改成 `ReentrantLock`。
- **没有排队语义**：virtual 的过载保护是"同时执行数上限"（缺省 10000），超过立即拒绝，不排队。下游资源（连接池、数据库）的上限要靠这个数或下游自己的限流来守，
  缺省 10000 往往远大于下游能承受的并发。
- **GC**：每请求一个虚拟线程与栈块，服务端 GC 停顿是固定池的数倍（本实验 16 ~ 19 vs 0 ~ 4ms / 35s，仍只占窗口 < 0.1%）。
- ThreadLocal / MDC：每个请求是一个新线程，ThreadLocal 不跨请求复用（缓存类用法失效，但也不会串数据）；本实验没有单独测量。

**固定池的边界也要知道**：有界队列只在"在途 > 线程 + 队列"时拒绝；若"排队上限 × 业务时长 / 线程数"接近调用超时，过载时队列里的请求会全部超时作废（E 组：
每秒 8.4 万次拒绝、成功率约 0）。阻塞型业务继续用固定池时，按"线程数 ≥ 阻塞时长 × 峰值 QPS"配线程，并把队列配到"排队等待远小于超时"。
