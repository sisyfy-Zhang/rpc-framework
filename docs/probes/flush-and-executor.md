# flush 合并与 direct 执行器对照实验（任务 14，阶段 2b 第一项）

回答阶段 2a 调研（[transport-path-comparison.md](../research/transport-path-comparison.md)）排在前面的两个候选项到底值多少：
候选 #1 `FlushConsolidationHandler`（T3-a）与候选 #3 服务端 `ExecutorConfig.direct()`（T2-a），以及本框架真实的单连接上限。
数据来自 `bench/bin/sweep.sh` / `bench/bin/compare.sh`，每组的原始 JSON / Markdown 在 WSL 的 `~/t14/out/formal/`（不入库）；
本文的表格由那些 JSON 机械整理（`extract.py`：每份结果取正式轮），数字未改动。**本文只给数据与建议，缺省值由主模型裁定。**

## 目的

1. **E1 flush 合并 A/B**：两端 pipeline 首位的 `FlushConsolidationHandler(256, true)` 对吞吐、延迟、每请求 `write` 系统调用数的影响；
   开环卡的 p50 / p99 是否回退（候选清单里唯一的风险项："低并发时 flush 多排一轮任务队列"）。
2. **E2 执行器**：服务端 `fixed`（缺省）vs `direct`（opt-in）；再与 gRPC `--executor direct`（directExecutor）的 1 / 2 个 channel 并排。
3. **E3 单连接上限**：每节点 1 条连接时本框架（fixed / direct）vs gRPC 单 channel（缺省执行器 / direct）——调研里"每连接 42k vs gRPC direct 单连接 65k"的实测版本。

## 方法

| 实验 | 变量 | 卡 | 怎么跑 |
|---|---|---|---|
| E1 | 两端 `flushConsolidation` on / off（同一构建，命令行切换） | `compare-closed64-rpc-v1`、`sweep-c1-closed64-rpc-v1`、`compare-open10k-rpc-v1` | `SWEEP_SERVER_ARGS="--flush-consolidation <on\|off>" BENCH_HARNESS_OPTS="--flush-consolidation <on\|off>" sweep.sh --cards ...` |
| E2 | 服务端执行器 fixed / direct | `compare-closed64-rpc[-direct]-v1`、`compare-open10k-rpc[-direct]-v1`；gRPC：`compare-*-grpc-v1`、`compare-*-grpc-c2-v1` | rpc direct：`sweep.sh --cards <三张 -direct 卡>`（执行器取自卡片 `target.server_executor`）；gRPC：`COMPARE_SERVER_ARGS_GRPC="--executor direct" compare.sh --transports grpc,grpc-c2`（结果目录名带 `nondefault`） |
| E3 | 每节点 1 条连接 | `sweep-c1-closed64-rpc[-direct]-v1`、`compare-closed64-grpc-v1`（缺省 1 个 channel） | 同上；gRPC 缺省执行器：`compare.sh --transports grpc --loads closed64` |

- rpc fixed 的数字取 E1 的 flush on 一侧（同一构建、同一张卡、同一时段，不重复跑）。
- 每组跑 2 次，**交替**：第 1 次按 E1-on → E1-off → rpc direct → gRPC direct → gRPC 缺省，第 2 次倒序（E1 变成 off → on）。表里每格两个数 = 两次运行各自的正式轮（闭环取窗口吞吐中位那一轮，开环取 p99 中位那一轮）。
- 先用 20s 缩短卡（每轮 20s、预热 5s、窗口 [5s, 18s]、3 轮，不入库）跑一遍确认流水线与量级，再用仓库的 60s 正式卡（每轮 60s、预热 20s、窗口 [20s, 55s]、3 轮）跑 2 次；下文全部是正式卡的数字。
- 指标：吞吐、p50 / p99（开环另看服务时间 p99）、两组核的平均忙碌率（`rounds[].cpu`）、每请求 `write` 系统调用（`rounds[].io.*.syscw_per_request`）、
  每请求上下文切换（自愿 + 非自愿，`rounds[].io.*.vol_cs_per_request + nonvol_cs_per_request`）、窗口内 GC 停顿（`rounds[].gc.*.pause_ms`，窗口 35s）。
  `syscw` 来自 `/proc/self/io`，**包含 eventfd 唤醒**（Netty `selector.wakeup()` 的 `write`），不只是套接字写；口径见 [benchmarking.md](../benchmarking.md#统计口径)。

  各自的轮间极差 ≤ 3%。p50 降 18% / 33%，p99 降 14% / 16%（两次运行的均值）。
- **写系统调用**：每请求 `write` 从约 1.0（每个请求 / 回包一次 flush）降到 0.09 ~ 0.19，两端都是；服务端在 2 连接时同时省掉了约 9 个百分点的服务端核

  `write` 次数基本不变（客户端 1.82、服务端 1.68 vs 1.73；超过 1 的部分是 eventfd 唤醒），所以合并本来就没有东西可合并，
  "flush 多排一轮任务队列"的代价也没有在 p50 上显出来。

读法：

- **direct 在 1KB 回显上是大头**：闭环 +35%（144.2k vs 107.2k），服务端核从约 49% 降到 26%（服务端每请求的 CPU 降了一半多），
  服务端每请求上下文切换 0.27 → 0.04（业务池的 park / unpark 没了）；开环 p50 0.37 → 0.25ms，p99 0.71~0.88 → 0.48~0.54ms，服务时间 p99 降约 38%。
  这与调研 T2 的推断一致（量级推断 1.3 ~ 2×，实测 1.35×）。
- **闭环 direct 不是服务端上限**：服务端核只用到 26%、客户端核 60%（压测端 5 核里约 3 核在忙），两侧都没饱和、`client_bound` 为否——2 条连接下
  更可能卡在客户端每条连接的那一个 IO 线程上（它做响应解码与回调链，调研 T1 ③）。这一点本实验没有按线程测 CPU，是推断；验证要 `top -H` 或 JFR 按线程的采样。
- **与 gRPC direct 并排**：同样"业务在 IO 线程上"，本框架 2 连接 144k vs gRPC 2 个 channel 75 ~ 82k；开环 p50 0.25 vs 0.35ms。
  gRPC 客户端每请求 1.4 次 `write`、1.2 ~ 1.3 次上下文切换（本框架 0.18 / 0.25），客户端核更高——差距主要在 gRPC 客户端路径（阻塞 stub 每次调用的
  HTTP/2 帧与唤醒），这不是本任务要解释的，只记录。gRPC c2 第 1 次运行三轮吞吐 70k ~ 82k，可重复性比单 channel 差。
- **fixed（缺省，flush on）已经高于 gRPC direct**：107k vs 76 ~ 82k（闭环）；开环 p99 两者在同一区间（0.71 ~ 0.88 vs 0.71 ~ 0.87）。

读法：

- 调研里的"每连接 42k"是 2 连接 83k 的平均数，不是单连接上限：同一构建关掉 flush 合并时单连接是 68 ~ 69k，开着是 98 ~ 99k。

  上限落在某一端的那一个 IO 线程上（direct 把服务端那一侧降到 16% 后吞吐只再涨 25%，说明客户端那一侧的 IO 线程占比更大；推断，未按线程测）。

## 结论

1. **flush 合并（候选 #1）有效且无可见代价**：闭环吞吐 +20%（2 连接）/ +44%（1 连接），p50、p99 同时下降，两端每请求 `write` 降一个数量级；
   开环 10000 req/s 的 p50 不变、p99 在轮间波动内。上下文切换不变——它不替代写队列 / direct。
2. **direct 执行器（候选 #3）在微秒级回显上收益最大**：闭环再 +35%、开环 p50 −33%、服务端 CPU 减半；但它的代价（阻塞即卡住同一事件循环上的所有连接）
   本实验**没有测**——1KB 回显是 direct 的最好情况，任何阻塞或毫秒级业务都会让它变差，结论不能外推到一般业务。
3. 下一个瓶颈（推断）：客户端每条连接的 IO 线程（响应解码 + 回调链），对应调研候选 #6（同步路径延迟解码）与 #5（合并完成依赖链）；
   验证需要按线程的 CPU（`top -H` / JFR `jdk.ExecutionSample`），本任务已加 `BENCH_JFR=1` 开关，未在本实验中使用（`settings=profile` 有开销，不与正式数字混用）。

## 对缺省值的建议（裁定权在主模型）

- `flushConsolidation`：**建议保持缺省 on**（两端）。依据：上表 E1；开环无回退；不改协议字节、不加定时器；off 仅保留给 A/B。
- `ExecutorConfig.direct()`：**建议保持 opt-in**，缺省仍为 fixed。依据：收益真实（E2），但隔离性代价未测且与"默认不牺牲隔离性"冲突；
  对外的数字应分开报"开箱即用（fixed + flush on）"与"非缺省（direct）"。
- 对比口径提示：flush 合并改变了 `compare-*-rpc-v1` 的缺省行为，下一次阶段归档的 rpc 数字会整体上移（闭环约 +20%），与 d5d620c 归档不可直接并排，
  归档说明里要写明这一点。

## 局限

- 单机、单次时段、宿主有桌面负载；每组只有 2 次运行。闭环各组之间的差距远大于轮间 / 运行间极差，开环 p99 的差异则在波动之内。
- `syscw` 包含 eventfd 唤醒，不能直接当作"套接字写次数"；上下文切换按存活线程求和，窗口内退出的线程计数丢失（本次 `threads` 两次快照之差 ≤ 1）。
- 没有按线程的 CPU，"瓶颈在客户端 IO 线程"是推断。
- direct 的隔离性（阻塞业务方法对同事件循环其它连接的影响）未测。
