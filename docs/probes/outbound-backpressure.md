# 出站背压（任务 16，阶段 2b 第三项，缺陷 F1）

回答两件事：阶段 2a 传输路径调研的缺陷 F1——两端都不检查
`Channel.isWritable()`，一个只发请求不读响应的客户端能让服务端回包在 `ChannelOutboundBuffer`（直接内存）里无界堆积——修好之后
积压被封顶到多少；以及缺省开启后正常负载是否变慢。这是正确性 / 健壮性修复，不是吞吐优化。**本文只给机制与数据，缺省水位线由主模型裁定。**

**结论：缺省开启的出站背压在正常负载下没有可测的代价**——闭环 2 连接 / 1 连接两组正式轮相对 off 为 −1.5% / +0.5%、+0.1% / +1.3%（门槛：
不低于 −2%），开环 p99 区间重叠，direct 执行器对照 −1.5%；正式卡 14 次运行、42 个轮次里服务端暂停读次数为 0（对端正常读时停读从不触发）。
"只发不读"的客户端下，服务端积压从 22.8MB（背压关）降到 0.16 ~ 0.35MB。

## 机制

### 服务端（缺省开，`RpcServerConfig.outboundBackpressure`）

- **读侧背压**：已接受连接的 pipeline 在 FlushConsolidationHandler 之后加一个 `OutboundBackpressure`（server 包，每连接一个实例）。
  `channelWritabilityChanged` 里看 `channel.isWritable()` 的**当前值**：不可写且没停过 → `setAutoRead(false)`、计 `autoReadPauses`；
  可写且是自己停的 → `setAutoRead(true)`。停读之后不再读这条连接的新请求，已在途的照常完成，积压被"在途数 × 回包帧"封顶；
  对端读走回包、待写字节降到低水位以下时恢复读，暂停期间对端写来的请求留在内核接收缓冲区里，恢复后照常读出。
  - 为什么按当前状态对账而不是按事件方向切换：FlushConsolidationHandler 收到"变为不可写"时先冲刷它推迟的 flush，套接字一次收下时
    这次冲刷**嵌套**触发"恢复可写"，先于外层的"不可写"到达下游。
  - 为什么是单独的 handler：背压关（A/B 对照）时它根本不在 pipeline 里；它只覆盖 `channelWritabilityChanged`，读事件
    （`ChannelInboundHandlerAdapter` 的方法带 `@Skip`）根本不经过它，正常负载下的成本是零；可以用 EmbeddedChannel 单独测。
- **硬上限**（兜底，`outboundHardLimit`，缺省 high × 16 = 1MiB，0 = 关闭，只在背压开时生效）：ServerHandler 分发 REQUEST 之前读一次
  该连接的 `totalPendingWriteBytes`，超过硬上限时不交给业务执行器、直接回 SERVER_OVERLOADED（业务没执行，客户端可安全换节点重试），
  计 `outboundOverloadRejections`，每连接第一次记 warn。回包里的原因是固定短常量 `"server overloaded: outbound buffer"`，
  待写字节与硬上限只进那一行 warn——被拒绝时连接本来就不可写，拒绝帧多带的每个字节都加进积压。选"回 SERVER_OVERLOADED"而不是"不分发"：不分发的请求没有回包，客户端只能等到超时。
  时序：停读在越过高水位的那一刻同步生效（事件循环上写进出站缓冲区 → 同步触发可写性事件），之后读循环不再继续读；会落到硬上限的只有
  **停读之前已经读进来的那一批帧**（当前读缓冲区里还没解码完的部分，最多一个读缓冲区，自适应分配器上限 64KiB）——direct 执行器下
  它们的回包在读循环内同步写出，小请求换大回包时这一批能把积压推得很高，硬上限就是防这个。
- **与读空闲的交互**：服务端 `IdleStateHandler(30, 20, 0)` 的读空闲照常计时；停读持续超过 30s，ServerHandler 关闭连接。对"长期不读的
  客户端"这是可接受的兜底（它的回包本来也送不出去）。读空闲阈值不可配，生产行为写在配置文档里；测试用 1s 的 IdleStateHandler 构造
  同一条路径。心跳不错乱：服务端的 pong 只回应已经读到的 ping（停读期间读不到 ping，也就不回），按出站顺序排在积压之后；
  服务端写空闲时主动发的 ping 照常排进出站缓冲区。
- 水位线 `writeBufferWaterMark(low, high)`（缺省 32KiB / 64KiB = Netty 缺省）不论背压开关都设到子连接上。

### 客户端

- 水位线同名可配，设到每条连接。
- **取连接时优先可写的连接**（`ConnectionPool.acquire`，调用方线程上一读 volatile 的事）：轮询到已激活但不可写的连接时继续看下一条，
  找到可写的就用它并计 `unwritableConnectionSwitches`；全都不可写时交出轮询到的第一条（照常写，不阻塞、不自旋）。
  不在事件循环上重新选连接：那要把请求从一个事件循环转投另一个。
- **硬上限**（`outboundHardLimit`，缺省 high × 16，0 = 关闭）：`writeOnEventLoop` 时连接不可写且待写字节超过硬上限，请求不写出，
  以 `RpcException("... request not sent")` 失败、计 `sendBufferRejections`、每连接第一次 warn。它走 RpcClient 的"传输失败"通道
  （不是超时、序列化、deadline），FailoverCluster 在 `retries > 0` 时换节点重试，failfast 直接给调用方。取连接时已优先可写的连接，
  拿到不可写的说明这个节点的连接都不可写。
- 客户端没有停读：它的积压本来就受"调用方并发 × 超时"约束。

## 阈值的计算

- Netty 的待写字节（`totalPendingWriteBytes`，可写性判定用同一个数）= 出站缓冲区里每条消息的字节数 + 每条目 96 字节记账开销，
  再加上事件循环外提交、还没执行的写任务的估算（非 ByteBuf 消息按 8 字节 + 每任务 32 字节）。业务线程的回包是 `RpcMessage`，
  在写任务里还只计约 40 字节，编码成帧（事件循环上）之后才按真实字节计入——**fixed 执行器下排队中的回包几乎不占水位线**。
- 1KB 回显的回包帧约 23（帧头）+ 值信封 + 1024 ≈ 1.06KB，加记账开销约 1.15KB。高水位 64KiB ≈ 56 个回包同时在出站缓冲区里。
- `compare-closed64-rpc-v1`（2 连接、64 并发）每连接最多 32 个在途，回包同时堆在出站缓冲区里也只有约 37KB < 64KiB；
  `sweep-c1-closed64-rpc-v1`（1 连接）最多 64 个在途 ≈ 74KB，只有在 flush 合并把一批回包攒到一起、且套接字一次写不完时才可能越过高水位
  ——越过时 FlushConsolidationHandler 先冲刷，套接字收下就嵌套恢复可写，不会停读。预期：**对端正常读的负载下暂停读次数为 0**，
  只有套接字发送缓冲区真的满了（对端读得慢）才会停读。正式卡数据与此一致（14 次运行、42 个轮次全部为 0）。
- 停读后的积压上界：fixed 执行器 ≈ high + (threads + queue) × 回包帧（停读时已读进来、还没回包的请求最多是执行器容量）；
  direct 执行器 ≈ high + 一个读缓冲区（≤ 64KiB）里的请求数 × 回包帧，超过硬上限的部分换成小的拒绝帧。

## "只发不读"对照测试

`steadyrpc-core` 的 `server/NonReadingClientTest`：原始 Netty 客户端（autoRead=false，按协议编码请求帧）向真实的 NettyServer（fixed(4, 1000)、
缺省水位线与硬上限、flush 合并开）发**固定总量** 20,000 个请求（每个要 1KB 回包，回包总量约 21MB），每批 100 个、批间 1ms，期间完全不读；
两端套接字缓冲区固定为 64KiB（不让内核自动调整吸收回包）。服务端那条连接的待写字节峰值由 pipeline 最靠近 transport 处的记录 handler
在每次写之后取。之后客户端恢复读。全程在 ByteBuf 泄漏探针（PARANOID）下运行。Windows 本机（2026-10-20，工作区未提交）：

| | 待写字节峰值 | 断言 | 暂停读次数 | 客户端开始读之前写进出站缓冲区的回包 | 恢复读后 |
|---|---|---|---|---|---|
| 背压开 | 155,655 / 345,900 字节（两次运行） | ≤ high + (4 + 1000 + 1) × 1,164 = 1,235,356 | 1 | 316 / 500 个 | 20,000 个回包全部收到（全部 OK），在途与待写字节归零、读恢复，后续请求正常，无泄漏 |
| 背压关（对照） | 22,847,848 字节（两次运行相同） | ≥ 15MiB 且 > 10 × 开的上界 | 0 | 20,000 个（全部） | 同上 |

背压开时峰值是关时的 0.7% ~ 1.5%；它只读进了几百个请求就停了，回包积压由"停读时的在途数"决定，与客户端发了多少无关。

硬上限（`server/OutboundBackpressureTest`，写不出去的 EmbeddedChannel，水位线 8KiB / 16KiB、硬上限 32KiB、direct 执行器、flush 合并开）：
一个读缓冲区里的 200 个请求（每个要 1KB 回包）——越过高水位时停读 1 次，这一批帧照常解码；分发了 29 个，其后 171 个因待写字节超过硬上限
不分发、回 SERVER_OVERLOADED（计数 171），待写字节 60,626 字节（≤ 32KiB + 2KiB + 171 × 192 = 67,648）；写走积压后读恢复，
29 个 OK + 171 个 SERVER_OVERLOADED（原因均为固定常量），在途归零，无泄漏。拒绝帧（含 96 字节记账开销）每个约 156 字节；
原因文本缩短之前是约 288 字节（同一场景待写字节 83,198），积压里这一部分随一批帧的数量线性增长。

其余测试：停读期间读到的 ping 照常回 pong、排在积压之后；FlushConsolidationHandler 嵌套恢复可写时读不会停在错误状态；停读超过读空闲阈值
（构造为 1s）时连接被关闭、积压随之释放；客户端多连接时不可写的连接一个请求都不分到、恢复可写后回到轮询；客户端连接对端是"接受但不读"的黑洞、
积压超过硬上限时请求以"request not sent"失败，failover（retries=1）全部换到健康节点成功，retries=0 时调用方看到这个传输失败；配置校验与接线
（两端连接的水位线、背压关时 pipeline 里没有 handler）；starter 属性（`64KB` 写法与纯数字字节）；Micrometer 计数器的注册与解绑。

## 正式卡（WSL 绑核，60s）

**预登记门槛**：缺省配置（背压 on、32K/64K）下 `compare-closed64-rpc-v1` 与 `sweep-c1-closed64-rpc-v1` 吞吐相对 off **下降不超过 2%**
（两组都成立），`compare-open10k-rpc-v1` p99 区间与 off 重叠；同时报告每轮暂停读次数。判定按正式轮（闭环取窗口吞吐中位那一轮），各轮区间并列。

方法同任务 14 / 15：`SWEEP_SERVER_ARGS="--outbound-backpressure <on|off>" bash bench/bin/sweep.sh --cards compare-closed64-rpc-v1,sweep-c1-closed64-rpc-v1,compare-open10k-rpc-v1`，
一次 sweep 一个服务端进程依次跑三张卡；第 1 组 on → off，第 2 组 off → on；然后 `compare-closed64-rpc-direct-v1` on / off 各 1 次。
客户端不变（背压是服务端开关），压测端客户端的未发出数与换连接次数进 `rounds[].backpressure.window.client_*`；flush 合并保持缺省 on。
环境同任务 15（WSL2 Ubuntu 10 vCPU，服务端绑 0-4、压测端 5-9，`-Xms1g -Xmx1g -XX:+AlwaysPreTouch`）；宿主关掉了桌面应用（只留一个编辑器窗口，
开跑前宿主 CPU 5 ~ 8%）。代码 9f3ec8c + 本任务工作区（`git_dirty = true`，探针口径）。时间 2026-10-21 13:01 ~ 14:00，14 次运行全部判定通过、
窗口内 0 错误。原始结果在 WSL 的 `~/t16/out/formal2/`（不入库），表格由那些 JSON 机械整理。

## 局限

- 单机、单时段；每组 2 次（direct 1 次）。第 2 组 2 连接各有一轮宿主瞬时停顿（见上），按正式轮中位数判定不受影响。
- 对端正常读的负载下停读从不触发，正式卡只能证明"没有代价"，证明"有效"的是"只发不读"对照测试。
- "只发不读"测试在 Windows 本机、loopback、固定 64KiB 套接字缓冲区下；Linux 上内核吸收的量不同，但断言的上界只依赖执行器容量与水位线。
